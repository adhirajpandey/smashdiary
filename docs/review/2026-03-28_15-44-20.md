# Codebase Review

Reviewed at: `2026-03-28 15:44:20`

Scope:
- Full repo review of the currently implemented codepaths
- No standalone plan document exists in the repo, so the implemented routes, services, repositories, and UI flows were treated as the effective plan
- Architecture question resolved during review: the app is intentionally `single-user / trusted-only`

## Executive Summary

The codebase has a sensible top-level shape for a small personal app: thin App Router pages, internal JSON APIs, a service/query/command split, and a repository seam that keeps Postgres and SQLite test mode largely aligned. The strongest architectural choice is the repository boundary plus duplicated DB constraints, which protects core match invariants even when validation is bypassed.

The main weaknesses are not correctness bugs in the happy path. They are scaling and maintenance risks:
- Dashboard, matches, and stats all load the full match set and full player set, then filter and derive in memory.
- Postgres and SQLite write logic are duplicated enough that future behavior drift is likely.
- Error handling at the HTTP and client transport boundary is broad and lossy, so real production failures will be harder to diagnose than they need to be.
- Test coverage is good for the main happy-path UX flows, but several branch paths and user edge cases are still uncovered.

No CI/CD or distribution workflow is defined in the repo. The build artifact is effectively the standard Next.js production output from `npm run build`, and publish/update strategy is currently deferred or manual.

## 1. Architecture Review

### Overall System Design And Boundaries

What is working well:
- `src/app` stays mostly thin and delegates real work downward.
- Internal JSON route handlers under `src/app/api` give the UI a stable boundary instead of coupling components directly to repositories.
- The read path is consistently shaped: route handler -> service -> query -> repository -> selectors/view model.
- The write path is also consistent: route handler -> service validation -> command -> repository transaction.
- Postgres and SQLite both enforce business-critical constraints at the DB layer.

Boundary concerns:
- The service layer is very thin. That is fine today, but it means most business behavior actually lives in repositories and selectors rather than in clearly named application services.
- The repository interface is clean, but the implementations duplicate non-trivial write behavior instead of sharing more of the algorithm.
- The compatibility aliases under `/api/games` widen the public internal surface area without adding much architectural value.

### Dependency Graph And Coupling

Healthy coupling:
- UI depends on API client hooks, not DB or repository modules.
- Query and command modules both depend on the repository selector, which is the right seam for runtime-mode switching.
- Validation is centralized in `src/lib/domain/matches.ts`.

Coupling risks:
- `src/lib/services/shared.ts` couples screen-data assembly to full-table fetches from both matches and players. Every dashboard, stats, and matches request pays that cost.
- `src/lib/match-selectors.ts` is doing a large amount of application behavior. That is fine for a small app, but it is now effectively a core domain service without being treated like one.
- Legacy naming and adapter files (`game` vs `match`, `src/lib/store.ts`) increase cognitive coupling and create drift risk.

### Data Flow And Bottlenecks

Primary bottleneck:
- `getMatchesAndPlayers()` in `src/lib/services/shared.ts` loads all matches and all players for dashboard, matches, and stats. Filtering for the selected player happens after the full read.
- This is acceptable for a small personal diary, but it is the main scaling ceiling in the current design.

Secondary bottlenecks:
- `listMatches()` resolves every match by joining all four player slots, then sorts in application memory.
- There is no pagination for match history.
- There is no cache or precomputation for leaderboard/stat derivation.

### Scaling Characteristics And Single Points Of Failure

Scaling characteristics:
- Reads are `O(total matches + total players)` for several screens, even when the user only needs one player's subset.
- Derived stats and leaderboard computation are repeated per request.
- Match detail is much better behaved because it scopes to one record.

Single points of failure:
- The selected repository backend is a hard dependency for all reads and writes.
- In default mode, Postgres connectivity is a single backend dependency.
- In test mode, the process-local SQLite seed bootstrap is a single local dependency.
- The client depends on every API response being valid JSON. If that contract breaks, transport failures become noisier than necessary.

### Security Architecture

Resolved assumption:
- Missing auth and authorization are accepted because the app is intentionally `single-user / trusted-only`.

Security review under that assumption:
- The internal API boundary is structurally clean.
- There is no server-side auth gate, but that is consistent with the accepted product boundary.
- Input validation is strong for match payloads.
- DB constraints backstop application validation correctly.
- There is no obvious SQL injection issue in the current repository code.

Residual risk:
- If this app is ever exposed beyond a trusted environment without adding auth, every `/api/*` route becomes a full read/write data surface immediately.

### Production Failure Scenarios Per Codepath / Integration Point

| Codepath | Realistic failure scenario | Accounted for? | Notes |
| --- | --- | --- | --- |
| Dashboard read | Postgres becomes slow or unavailable; `/api/dashboard` throws | Partially | User gets a generic 500/UI error state, but root cause is not logged in the route layer |
| Matches read | Match table grows large; every request scans and resolves all matches | No | Current shape works only while dataset stays small |
| Stats read | Leaderboard/stat computation becomes slow with large history | No | No aggregation, pagination, or cache layer |
| Match detail read | Match deleted between navigation and fetch | Yes | `404` path exists in API and UI |
| Create match | Two rapid submits create duplicate matches | No | Button disables visually, but submit handler has no hard in-function reentry guard |
| Update match | Match deleted in another tab before save | Yes | Repository throws `MatchNotFoundError`, surfaced as `404` |
| Delete match | API returns HTML or malformed JSON during failure | No | `fetchJson()` assumes JSON and can throw a secondary parse error |
| Clone preload | Source match missing or deleted | Yes | UI falls back to a fresh entry and shows clone error text |
| Identity picker preload | Stored `selectedPlayerId` no longer exists | Yes | Picker clears invalid local selection after players load |
| Repository mode selection | `DATABASE_URL` missing in default mode | Yes | App fails fast when DB is first touched |
| SQLite test mode bootstrap | Seed JSON shape drifts from SQLite schema | Partially | Boot fails loudly, but there is no explicit schema/seed contract test |

### Architecture Findings

#### A1. Full-table read architecture is the primary scaling limit

Severity: Medium

Files:
- `src/lib/services/shared.ts`
- `src/lib/queries/matches.ts`
- `src/lib/queries/players.ts`
- `src/lib/repositories/postgres-match-repository.ts`
- `src/lib/repositories/sqlite-match-repository.ts`

Why it matters:
- Dashboard, matches, and stats all fetch all matches and all players, then filter/derive in memory.
- This is the dominant read cost in the app and will become the first real bottleneck as the diary grows.

Recommendation:
- Keep the current architecture for now if the app remains small.
- If you expect continued growth, push selected-player filtering and some leaderboard/stat aggregation into repository queries.

#### A2. Repository implementations are aligned in behavior but too duplicated in write logic

Severity: Medium

Files:
- `src/lib/repositories/postgres-match-repository.ts`
- `src/lib/repositories/sqlite-match-repository.ts`
- `src/lib/repositories/shared.ts`

Why it matters:
- Both repositories independently implement player upsert, roster slot mapping, normalization, update/create branching, and delete flow.
- The more features you add, the more likely Postgres and SQLite drift.

Recommendation:
- Keep backend-specific SQL where necessary.
- Move more backend-agnostic write algorithm steps into shared helpers or contract tests.

#### A3. Compatibility alias routes add surface area without much payoff

Severity: Low

Files:
- `src/app/api/games/route.ts`
- `src/app/api/games/[id]/route.ts`

Why it matters:
- They are cheap now, but they are another API surface to preserve indefinitely.
- They also preserve old terminology that the rest of the app is trying to move away from.

Recommendation:
- If external clients do not rely on them, deprecate them.
- If they must stay, document them explicitly as compatibility aliases.

## 2. Code Quality Review

### Code Organization And Module Structure

Strong points:
- Clear split between route/UI code and persistence code
- Good use of small query and command adapters
- Validation and selector logic are easy to find
- Tests are colocated well for unit-level modules

Weak points:
- Service modules like `dashboard.ts`, `matches.ts`, `stats.ts`, and `players.ts` are so thin that they mostly act as pass-through layers.
- A large amount of real behavior is concentrated in `src/lib/match-selectors.ts` and the repository implementations.
- Legacy naming around `game` vs `match` remains spread across types, helpers, and compatibility modules.

### DRY Violations

Aggressive callouts:
- Postgres and SQLite repositories duplicate the player-upsert algorithm and save/delete branching.
- The route handlers for dashboard, stats, matches, and players all repeat the same `try/catch -> jsonSuccess/jsonServerError` pattern.
- The page clients for dashboard, matches, and stats repeat the same `isHydrated/isPending/error/success` rendering structure.

These are not all worth refactoring immediately. The repository duplication is the one most likely to cause real future drift.

### Error Handling Gaps And Missing Edge Cases

#### Q1. `fetchJson()` assumes every response body is valid JSON

Severity: Medium

File:
- `src/lib/api/client.ts`

Risk:
- If Next.js emits an HTML error page, a proxy injects a non-JSON response, or the body is empty, `response.json()` throws before the app can normalize the error.
- Users can then see a generic low-quality transport failure instead of the intended app error.

Missing tests:
- Non-JSON 500 response
- Empty body response
- Invalid JSON on failed delete/create/update

#### Q2. Match submit flow does not hard-block reentry in `handleSubmit`

Severity: Medium

File:
- `src/app/_components/game-form.tsx`

Risk:
- The submit button is disabled while pending, but the submit handler itself does not bail out when a mutation is already in flight.
- Rapid double submit via keyboard or timing edge cases can produce duplicate creates.

Missing tests:
- Rapid double submit
- Slow network while user presses Enter twice

#### Q3. GET routes swallow failure context

Severity: Low

Files:
- `src/app/api/dashboard/route.ts`
- `src/app/api/matches/route.ts`
- `src/app/api/matches/[id]/route.ts`
- `src/app/api/players/route.ts`
- `src/app/api/stats/route.ts`

Risk:
- These handlers return clean user-facing messages, but they discard the original error and do not log route-level context.
- Diagnosis in production becomes slower than necessary.

Missing tests:
- Route service throw -> expected 500 branch for GET handlers

#### Q4. Cross-tab state sync is not handled for selected player

Severity: Low

File:
- `src/app/_components/selected-player-provider.tsx`

Risk:
- Changing selected player in one tab does not update another tab.
- This is acceptable for a personal app, but it is still a real UX inconsistency.

Missing tests:
- `storage` event handling does not exist

### Technical Debt Hotspots

- `src/lib/match-selectors.ts`: central and important, but growing into a catch-all derived-data module
- `src/lib/store.ts`: legacy compatibility adapter that can drift from current architecture
- `src/lib/supabase.ts`: empty file, likely stale scaffolding
- mixed `game` / `match` naming across types, repositories, APIs, and docs

### Over-Engineered vs Under-Engineered

Under-engineered relative to a pragmatic preference:
- filtered queries should happen lower in the stack once data volume grows
- transport error normalization should not depend on valid JSON from every failure path
- there is no operational deployment story in the repo

Over-engineered relative to the current product size:
- keeping `/api/games` compatibility aliases alongside `/api/matches`
- some UI interaction complexity in menu/focus management is substantial compared with the app's otherwise simple surface, though it is justified by the tested accessibility behavior

### Existing ASCII Diagrams

Findings:
- No meaningful ASCII diagrams were found in the implementation files reviewed.
- There is no stale diagram problem today because there are effectively no such diagrams to maintain.

Assessment:
- This app would benefit from a few doc-level diagrams.
- It does not need code-comment diagrams.

## 3. Step 1: Codepath Trace

### 3.1 Create / Update Match

```text
GameForm.handleSubmit
  -> build payload from component state
  -> if matchId exists?
       yes -> updateMatchMutation.mutateAsync(payload)
       no  -> createMatchMutation.mutateAsync(payload)
  -> success?
       yes -> success toast -> router.push(/matches/{id})
       no  -> error is ApiClientError?
                yes -> error toast -> fieldErrors state set
                no  -> generic failure toast

create/update mutation
  -> fetchJson(/api/matches or /api/matches/{id})
  -> network ok and JSON parse ok?
       no -> throw raw transport/parser error
       yes -> body.error?
                yes -> throw ApiClientError
                no  -> return body.data

POST/PUT route
  -> parseNumericId for PUT only
  -> invalid id?
       yes -> 404
       no  -> request.json()
                throws -> 400 invalid request payload
                works  -> saveMatchFromJson(body, optional id)
  -> switch result.type
       success -> 200/201
       validation_error -> 400
       not_found -> 404 for PUT, 500 fallback text for POST path
       internal_error -> 500

saveMatchFromJson
  -> gameFormSchema.safeParse(input)
  -> parse success?
       no -> normalized validation_error
       yes -> deriveWinnerSide -> saveMatch(command)
  -> save throws MatchNotFoundError?
       yes -> not_found
       no  -> save throws anything else?
                yes -> internal_error
                no  -> success

repository.saveMatch
  -> pick backend by runtime mode
  -> transaction
  -> normalize/upsert side A players
  -> normalize/upsert side B players
  -> normalize playedOn
  -> input.id exists?
       yes -> UPDATE games
                no row changed -> MatchNotFoundError
                row changed    -> return id
       no  -> INSERT games -> return id
```

Branch observations:
- Validation coverage is decent.
- Duplicate-submit branch is not tested.
- Non-JSON failure branch in `fetchJson()` is not tested.
- POST branch for `not_found` is structurally unreachable in normal design and currently maps to a 500 fallback string.

## 4. Step 2: User Flows, Interactions, And Error States

### Covered Main User Flows

Well covered by Playwright:

- create singles match
- create doubles match

Good:

Gaps:
- transport/parser failures can degrade into generic or confusing messages

### Empty / Boundary States

Handled in code:
- no selected player -> dashboard metrics hidden, matches empty, stats personal summary hidden

Insufficiently exercised:
- large match list
- empty players list in identity picker
- player name max length boundaries
- very old selected localStorage value combined with changed dataset

## 6. Performance Review

### N+1 Queries And Database Access Patterns

Good:
- No classic ORM N+1 issue was found in the main repository reads.
- Match resolution is done with one joined query rather than per-player follow-up queries.

Weaknesses:
- Several screens effectively do full-table scans and in-memory filtering.
- The app avoids N+1 but replaces it with coarse-grained over-fetching.

### Memory Usage Concerns

Main concern:
- Dashboard, stats, and matches all materialize full resolved match arrays and player arrays in memory.
- This is fine for a small diary and poor for long-term growth.

### Caching Opportunities

Low-risk opportunities:
- leaderboard/stat derivation cache per data version
- player-filtered history query at repository level
- paginated match history query

Current cache posture:
- React Query caches client-side responses, but every server request still recomputes everything.
- Query invalidation after mutations is correct but broad.

### Slow / High-Complexity Paths

Likely slowest paths as data grows:
- `getMatchesAndPlayers()` on dashboard, matches, and stats
- `getTopPerformers()` and per-player rating/stat derivation over the entire dataset
- `sortResolvedMatchesDescending()` after full read

## Final Assessment

For a personal, trusted-only badminton diary, the architecture is sound enough and the core flows are implemented cleanly. The main risks are future-facing: scale, backend drift between Postgres and SQLite, and untested failure branches around transport and concurrency. The codebase is in good shape for continued iteration if those risks are handled deliberately rather than left to accumulate.
